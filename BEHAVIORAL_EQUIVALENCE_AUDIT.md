# Behavioral Equivalence Audit Report
**Date:** 2026-07-28  
**Scope:** Legacy Docker Controller vs. Node Agent Executor runtime creation paths

---

## Executive Summary

This audit compares Docker container configuration generated by two runtime creation paths:

1. **Legacy Controller Path:** `internal/controller/docker_driver.go` (local single-server deployments)
2. **Node Agent Path:** `internal/nodeagent/executor.go` (production distributed deployments)

**Key Finding:** The two paths generate **mostly equivalent** Docker configurations with **one critical bug** in port environment variable injection for cpu_native and openai_compat backends.

---

## Cross-Cutting Differences

### Container Naming Strategy
| Path | Pattern | Purpose |
|------|---------|---------|
| **Legacy Controller** | `nexus-<sanitized-model-name>` | Simple, human-readable |
| **Node Agent** | `nexus-<model>-r<idx>-<suffix>` (HA) or `nexus-<model>` (single) | Unique per replica for HA |

**Classification:** **Intentional** — Agent supports multiple replicas of the same model

---

### Pre-flight Container Cleanup
| Path | Behavior |
|------|----------|
| **Legacy Controller** | `docker rm -f <name>` before `docker run` |
| **Node Agent** | `docker rm -f <name>` + `docker rm -f` for stale HA containers |

**Classification:** **Intentional** — Agent cleans up orphaned HA containers

---

### GPU Assignment Logic
| Path | CPU Mode | GPU Mode |
|------|----------|----------|
| **Legacy Controller** | No `--gpus`, no runtime override | `--gpus device=X,Y` |
| **Node Agent** | `--runtime runc` (explicit CPU-only) | `--gpus device=X,Y` or `--gpus all` |

**Classification:** **Intentional** — Agent prevents nvidia-runtime on GPU nodes for CPU workloads

## Critical Bugs Found

### Bug #1: Missing Port Environment Variables (cpu_native, openai_compat)
**Severity:** 🔴 **CRITICAL**

**Location:** `internal/controller/docker_driver.go:applyCommonResourceArgs`

**Root Cause:** The attempted fix to inject Backend.ContainerPortEnvVars() exists in the code but doesn't execute because:
```go
if d.registry != nil && spec.BindPort > 0 {
    backend := d.registry.BackendForType(spec.BackendType)
    for k, v := range backend.ContainerPortEnvVars(spec.BindPort) { ... }
}
```
The condition `d.registry != nil` fails at runtime — the registry was supposed to be passed in `cmd/admin/main.go` but the build failed.

**Impact:**
- faster-whisper-server (UVICORN_PORT) → binds to default port (often 8000)
- Kokoro TTS (PORT/HTTP_PORT) → binds to default port
- Infinity embeddings (PORT/HTTP_PORT) → binds to default port
- Custom OpenAI-compatible services (PORT/HTTP_PORT) → bind to default ports

**Manifestation:** Port conflicts, health check failures, "address already in use" errors

**Required Fix:** Complete the integration started in docker_driver.go by ensuring `NewDockerDriver(registry)` receives a valid registry reference in cmd/admin/main.go

---

### Bug #2: Missing Docker Health Check (llamacpp only)
**Severity:** 🟡 **MEDIUM**

**Location:** `internal/controller/docker_driver.go:buildLlamaCppArgs`

**Issue:** Node agent sets `--health-cmd` with dynamic `--health-start-period` based on model size. Controller path omits this entirely.

**Impact:** 
- Docker doesn't know when llama.cpp container is healthy
- External monitoring must probe /health endpoint
- No automatic unhealthy detection at Docker level

**Classification:** **Missing feature parity** — not breaking but reduces operational visibility

## Intentional Design Differences

### 1. Container Naming (HA Support)
**Why Different:** Agent supports multiple replicas (HA), controller is single-instance only

**Impact:** None (different use cases)

---

### 2. CPU Runtime Override
**Why Different:** Agent explicitly forces `--runtime runc` for CPU workloads to prevent nvidia-runtime misbehavior

**Impact:** Positive — prevents GPU runtime from interfering with CPU containers

---

### 3. Volume Names
**Why Different:** Agent uses backend-specific volumes (`llamacpp_models` vs. `nexus_models`) for isolation

**Impact:** Minor — operators must know which volume to populate

---

### 4. GPU Layer Handling (llamacpp)
**Why Different:** Agent respects `execution_mode` field (cpu/gpu/auto); controller infers from GPUDevices alone

**Impact:** Agent is more explicit and safer (prevents accidental GPU offload)

---

### 5. Health Check Strategy
**Why Different:**
- **Controller:** No health checks (expects external monitoring)
- **Agent:** Injects Docker health check for llamacpp; uses external watcher for others

**Impact:** Agent has better operational visibility for llamacpp workloads

---

## Obsolete Legacy Behavior

None identified — all differences are either intentional design improvements or bugs.

## Conclusion

The legacy Docker controller path and node agent executor path are **mostly behaviorally equivalent** with the following critical exceptions:

1. **cpu_native and openai_compat backends have broken port configuration** in the controller path (attempted fix incomplete)
2. **llamacpp backend missing Docker health check** in controller path (minor operational impact)
3. **Several intentional design differences** improve HA support, CPU/GPU isolation, and operational visibility in the agent path

The controller path is **production-broken** for cpu_native and openai_compat backends until the Backend interface integration is completed.
